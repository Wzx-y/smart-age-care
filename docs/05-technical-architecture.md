# 技术架构

## 通知与统一审计（阶段 5 源码补充）

`NotificationService` 将任务逾期、护理异常、入住确认和交接提交写入 `care_notification`；逾期扫描以“租户 + 广播接收者 + 任务去重键”防止重复创建。`AuditEventService` 只读合并 `care_audit_log`、`care_master_data_audit` 与 `care_export_audit`，统一返回最小化资源轨迹；保留清理由受控定时任务按配置执行。

## 运营报表与异步导出（阶段 5 源码补充）

`JdbcOperationalReportRepository` 通过租户范围 SQL 从入住、床位、长者、护理任务、服务记录和异常跟进项聚合运营指标。`ExportService` 将导出请求写入 `care_export_job`；`ExportGenerationScheduler` 领取 `QUEUED` 任务、生成只含数值指标的 CSV、写入私有对象存储并转换为 `READY`。下载接口只返回 5 分钟签名地址，且 `ExportJobView` 不序列化 `storage_key`。定时扫描将过期任务标记为 `EXPIRED`，应用层拒绝后续签名请求。

## 基础资料管理（阶段 2/3 源码补充）

`MasterDataController` 位于 `/api/v1/master-data`，每个入口先要求 `care:master-data:manage`，再由 `MasterDataService` 从可信 `TenantContext` 取得租户和操作者。JDBC 仓储对房间、床位和目录项的查询与写入均绑定 `tenant_id`；更新与启停带版本条件，并将最小操作记录写入 `care_master_data_audit`。入住床位仓储在查询和状态流转中同时排除已停用床位及已停用房间。

## 边界

前端为 React/Vite SaaS 工作台，负责展示、表单校验、路由状态和受控交互；不得持有服务角色密钥或直接调用模型。RuoYi 微服务作为认证、用户、租户、角色、权限、字典、审计与网关底座。养老业务服务承载长者、入住床位、护理、设备、告警、报表和导出。

## 集成

- RuoYi Gateway：验证令牌、解析当前用户和租户，向业务服务传递不可伪造的身份上下文。
- 业务服务：执行领域规则、事务、审计与数据范围校验。
- Supabase：可选的附件对象存储与受限下载签名，不承担 RuoYi 身份或租户权威来源。
- OpenAI：仅由服务端 AI 编排服务调用，使用知识库检索结果与最小必要数据，输出草稿供人工确认。

## 数据流与错误处理

浏览器 -> Gateway -> 认证/业务服务 -> 数据库或受控外部服务。Gateway 拒绝未认证、无租户和无权限请求；服务端统一返回可展示的错误码、追踪 ID 与重试建议。网络重试仅用于幂等读取、可恢复的任务提交和导出轮询；床位分配、入住确认、权限修改等写操作必须使用幂等键和乐观锁。

入住确认和退住均由 `care-service` 的同库事务执行：读取租户范围内的入住单与床位，使用版本号和当前状态作条件更新。确认原子写入床位占用、长者在院状态、入住单确认状态和最小化审计事件；退住原子解除长者床位绑定、将床位转为清洁中、写入退住原因和入住单退住状态，再写入最小化审计事件。所有资源查询均带 `tenant_id`；跨租户资源按 404 处理，不暴露存在性。事务回滚依赖受 Spring 代理管理的 JDBC 数据源，须在云端 MySQL 集成测试中验证。

入住调度读取模型在同一服务内完成关联查询：入住单查询联合长者、床位和房间，仅向前端返回调度所需的姓名、房间号、床位号、状态、版本号和预留截止时间；床位查询联合房间信息，返回占用与卫生状态。前端在 Gateway 模式中按当前会话令牌加载此模型，写入成功或收到 `409` 均重新查询，避免使用过期版本。床位预留写入 `reserved_until`，确认入住会拒绝已过期预留；调度器按受控间隔调用同一事务服务，原子释放床位、清空入住单床位关联并将状态恢复为待安排，随后仅记录关联 ID 的 `ADMISSION_RESERVATION_EXPIRED` 审计事件。

预留和确认写操作由幂等服务包裹在同一 JDBC 事务内。服务端以请求内容计算 SHA-256 指纹，先按租户、操作者、操作类型和请求键创建记录，再执行业务更新、审计与结果写入。唯一键竞争后使用 `SELECT ... FOR UPDATE` 当前读取得已提交结果，规避 MySQL 可重复读下的旧快照；业务异常会连同“进行中”记录一起回滚。

## 建议目录演进

`src/app` 放应用装配，`src/features` 放领域 UI 与用例，`src/lib` 放共享客户端和权限工具，`src/server` 放仅服务端适用的适配器，`src/types` 放共享契约；后端服务独立仓库或子目录部署，不把密钥逻辑放入浏览器包。

## 护理计划与任务实现（阶段 3 源码）

`care-service` 新增 `care` 领域包，Controller 仅处理 `/api/v1/care-plans` 与 `/api/v1/care-tasks` 的参数校验和统一响应；服务层从 Gateway 传入的可信 `TenantContext` 获得 `tenantId` 与操作者，不接收浏览器传来的租户字段。JDBC 查询和更新均包含 `tenant_id`。

计划创建和发布使用长者行锁串行化同一长者的版本分配和已发布计划替换，避免并发发布产生多个当前计划。任务创建也持有同一长者锁后重新读取计划状态。完成任务和 `care_service_record` 写入在同一数据库事务内，任一步失败均回滚；状态或版本未命中统一映射为 `409`。

护理写操作使用 `care_write_idempotency`：记录仅保存租户、操作者、操作、请求指纹、结果资源类型/ID、状态、版本和必要的异常或结案说明。唯一键竞争后使用当前读取得已提交结果，再按当前租户重新读取资源重放。异常任务在状态更新后同一事务创建 `care_task_follow_up`；开放跟进项的结案也使用版本条件更新与幂等重放。

RuoYi 成员目录已作为护理责任人和执行人的服务端校验边界：计划、模板和任务写入要求目标成员属于当前机构且具备对应权限。生产环境仍须通过实际 RuoYi、Gateway 和 MySQL 集成验证该边界，源码存在不替代运行证据。

React 的 `features/care/care-api.js` 在 Gateway 模式中使用既有 Bearer Token 读取计划、任务、模板、异常跟进项和班次交接，并提交计划创建/编辑/发布/停用、模板维护、按日任务生成、任务创建/开始/完成/异常、跟进结案和交接创建/提交；每次写操作由客户端生成或复用 `Idempotency-Key`。工作台通过长者和成员目录解析关联名称，目录加载失败时明确显示关联编号，不以本地示例冒充服务端结果。

## 长者档案闭环（阶段 2/3 源码）

`Resident360Service` 在可信租户上下文中聚合长者基础资料、健康档案、联系人、评估、附件、入住单、护理计划、任务和服务记录；各下游仓储均先按 `tenant_id` 查询，再按当前长者 ID 过滤。联系人与评估使用数据库版本号条件更新和删除，主联系人切换由事务包裹。`care_plan.assessment_id` 只保存同租户、同长者的评估引用，创建或编辑计划时服务端验证归属；被有效计划引用的评估不能删除。

React 工作台只在 Gateway 模式调用健康档案、360、联系人、评估和附件 API。附件访问地址由按钮点击时临时取得后直接打开，不进入 React 持久化状态、日志或审计正文。

## 入住与床位闭环（阶段 5 源码）

评估决策、调床和清洁记录由 `care-service` 在同一 JDBC 事务中处理。调床依次条件化占用目标床位、将原床位转为清洁、更新长者当前床位和入住单、写入最小审计；任一步失败均回滚。评估结论、调床理由和清洁结果单独按租户保存，不复制到通用审计正文。

## 护理执行闭环（阶段 3 源码补充）

任务开始、完成和异常均在 `care-service` 的同一事务中以任务版本和当前状态条件更新。开始仅允许 `PENDING -> IN_PROGRESS`；完成写入服务记录，异常写入跟进项，随后写入仅含任务、长者、操作者与动作的审计事件。所有操作依赖可信租户上下文与成员授权，客户端不传递租户字段。

## 机构成员目录与权限（阶段 1/3 源码补充）

`ruoyi-system` 使用 `care_tenant_member` 保存成员是否已加入机构，并使用 `care_tenant_member_role` 保存该成员在该机构内的 RuoYi 角色。`TenantMemberDirectoryMapper.selectPermissionCodes` 按 `tenant_id + user_id` 关联成员角色、RuoYi 角色菜单和菜单权限，因此护理服务不会再从全局 `sys_user_role` 推断机构内权限。

浏览器只发送当前选择的 `X-Tenant-Id` 请求头；Gateway 对 `/care/**` 和 `/system/tenant-members/**` 都先以内部成员目录校验令牌用户是否为该机构的启用成员，再移除浏览器可伪造头并注入可信 `X-Platform-Tenant-Id`、用户 ID 与内部凭据。成员管理控制器只接受该可信上下文，不能以请求体或查询参数覆盖租户。

React 的 Gateway 模式通过 `/system/tenant-members` 读取和维护机构成员，通过既有 `/system/user/list`、`/system/role/list`、`/system/menu/roleMenuTreeselect/{roleId}` 与 `/system/role/dataScope` 读取系统账号、角色、菜单摘要和数据范围。RuoYi 用户、角色、部门和菜单仍保持单一权威来源。
